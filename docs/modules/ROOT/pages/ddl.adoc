= Entities from DDL
:description: How tib generate entity reads the tables of SQL DDL into the entities of a service.

`tib generate entity --ddl FILE` reads the tables of SQL DDL into the spec of the service, the
one that `.tib/state.yaml` records, and generates the entity layer of its entities as it does from
a xref:spec.adoc[spec file]. The DDL of the example service:

[source,sql]
----
include::example$vehicle-service.sql[]
----

[source,bash]
----
$ tib init service vehicle-service
$ tib generate entity --ddl vehicle-service.sql --dry-run
$ tib generate entity --ddl vehicle-service.sql
Wrote 23 files to /home/you/vehicle-service.
----

== What tib reads

Each table that a `CREATE TABLE` statement creates is an entity, named after the table in upper
camel case and in the singular: `vehicles` is `Vehicle`, `VEHICLE_TYPES` is `VehicleType`. The
names of its fields are the names of their columns in lower camel case: `plate_number` is
`plateNumber`. The table and the columns keep their names.

The primary key, of one column, is the identifier. A UUID gets its value from the application; an
integer is a `Long` that the database assigns, by identity when the column says so
(`GENERATED ... AS IDENTITY`, `IDENTITY`, `AUTO_INCREMENT`, `SMALLSERIAL`, `SERIAL`,
`BIGSERIAL`), by a sequence otherwise.

A column that references another table, with `REFERENCES` or a foreign key, is a relation to the
entity of that table: many to one, or one to one when the column is unique. The relation is named
after the column without `_id`: `depot_id` is `depot`. The table may be in the DDL or be the table
of an entity that the service already has.

The columns `created_at` and `updated_at`, both timestamps with a time zone, make the entity
audited, as `audit: true` does in a spec. Every other column is a field, which accepts null unless
the column is `NOT NULL` and is unique when the column is or when a unique key has that column
alone.

[cols="2,1"]
|===
|SQL type |Field type

|`VARCHAR(n)`, `VARCHAR2(n)`, `NVARCHAR(n)`, `NVARCHAR2(n)`, `CHARACTER VARYING(n)`, `CHAR(n)`, `CHARACTER(n)`, `NCHAR(n)`, `TEXT`, `CLOB`, `NCLOB`
|`String`, of length _n_ when there is one

|`SMALLINT`, `INT`, `INTEGER`, `INT2`, `INT4`, `SMALLSERIAL`, `SERIAL`; `NUMERIC(p)`, `DECIMAL(p)` and `NUMBER(p)`, also with a scale of 0, up to nine digits
|`Integer`

|`BIGINT`, `INT8`, `BIGSERIAL`; `NUMERIC(p)`, `DECIMAL(p)` and `NUMBER(p)`, also with a scale of 0, up to nineteen digits
|`Long`

|`NUMERIC`, `DECIMAL` and `NUMBER` without digits, with a scale above 0, or with more digits
|`BigDecimal`

|`BOOLEAN`, `BOOL`
|`Boolean`

|`DATE`
|`LocalDate`

|`TIMESTAMP`, `TIMESTAMP WITHOUT TIME ZONE`, `DATETIME`
|`LocalDateTime`

|`TIMESTAMPTZ`, `TIMESTAMP WITH TIME ZONE`
|`Instant`

|`UUID`
|`UUID`
|===

The mapping does not go both ways, so the migrations that tib writes do not read back into exactly
their spec: a `BigDecimal` without a scale is a `NUMERIC(p, 0)`, which reads back as a `Long`, or an
`Integer`, when it has up to nineteen digits; a `String` without a length is a `VARCHAR(255)`,
which reads back with `length: 255`.

`ALTER TABLE` statements may add primary, foreign and unique keys to the tables created before
them. Every other statement, such as one that creates a sequence or an index, a comment or data,
or drops a table, is skipped; so are the defaults and checks of the columns and the unique keys of
several columns. SQL that tib cannot parse, DDL without a `CREATE TABLE`, a column of another
type, a table without a primary key, a primary or foreign key
of several columns, a reference to a table that is neither in the DDL nor in the service, a table
created twice, and an `ALTER TABLE` that changes anything else or comes before its table are
problems: tib reports each with the table and the column it is about, and writes nothing.

The spec that the DDL yields is checked as a xref:spec.adoc#_the_rules[spec file] is. A table or a
column named like a word that SQL reserves, or a column named like a Java keyword, is a problem
of the spec, which names the entity and the field as the spec sees them. For a table `user` with
a column `class`:

[source,text]
----
the spec has 2 problems:
  entities[0].table: 'user' is a reserved word in SQL; give the entity a table
  entities[0].fields[0].name: 'class' is a Java keyword
----

With DDL, the way out is to rename the table or the column in the DDL; a column named like a Java
keyword can also keep its name when the spec of the service gives its field another one, as in
`{ name: kind, type: String, column: class }`, which the field of the column then keeps.

== The spec of the service

The entity of a table takes the place of the entity of the same table in the spec of the service,
and keeps its name, its options and the names of the fields and relations of the same columns;
the entities of the other tables come after those of the spec. So the DDL gives the columns, and
the spec keeps what the DDL cannot say. The spec that results is the one `.tib/state.yaml`
records, and a second run with the same DDL changes nothing.

The migration of an entity is written once, from its spec, for PostgreSQL. After a change of the
DDL the files written on every run follow it; the change of a table that has its migration already
needs a new migration, which you write.
