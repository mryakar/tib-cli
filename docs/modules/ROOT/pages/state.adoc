= The state file
:description: .tib/state.yaml, the record of what tib generated in a service.

`.tib/state.yaml` is the record of what tib generated in a service: the versions of tib and of
the pack that wrote it, the files that the spec was read from, the spec, and every file that tib
wrote with its owner and the hash of its content. tib reads it at the start of a run and writes it
with every run that writes files; `tib status` compares the files of the service, and those that
the spec was read from, with it. Commit
it with the service, and do not edit it.

== An example

The state file of the service of xref:getting-started.adoc[], after
`tib generate entity --spec vehicle-service.yaml`, shortened:

[source,yaml]
----
# Written by tib on every run. Do not edit: your changes would be lost. # <1>
tib: 0.3.0
pack:
  name: default
  version: 0.3.0
  stack: Spring Boot 4
inputs:
- kind: spec
  path: vehicle-service.yaml
  sha256: 574dbfdaa1431ba5e7301ba45d919128b46f13e705ed5e6dab2b1f5421afcbfe
spec: # <2>
  tib: 1
  service: vehicle-service
  group: com.example
  pack: default
  entities:
  - name: Vehicle
    table: VEHICLE
    ...
files:
- path: .gitattributes
  owner: developer
  sha256: a91782176fa82dba11a5728b019708208fec6862455a52b134ddc598e8444346
...
- path: src/main/java/com/example/vehicleservice/vehicle/VehicleMapper.java
  owner: generator
  sha256: 79381ac95825a400cd490cc5e99223fce5a79dee62ff6263b89fa9be9c88131a
...
----
<1> The first line says that tib writes the file, as the first line of every generated file says
who owns it; a YAML reader skips it.
<2> The spec of the service with every value that tib derives filled in.

== The keys

[cols="1,3"]
|===
|Key |What it holds

|`tib`
|The version of tib that wrote the file.

|`pack.name`, `pack.version`
|The pack that generated the files, and its version. The version of the default pack is the
version of tib.

|`pack.stack`
|The stack that the pack generates for, such as `Spring Boot 4`; none in a state file that a tib
before 0.3.0 wrote.

|`inputs`
|The files that the spec of the service was read from, in the order tib first read them; none for
a service scaffolded from its name. A file read again takes the place of its earlier record. A
spec file is the whole spec of the service, so a run with one leaves it the only input.

|`inputs[].kind`
|`spec` for a spec file, `ddl` for SQL DDL.

|`inputs[].path`
|The path of the file.

|`inputs[].sha256`
|The SHA-256 of the content of the file when tib read it, which `tib status` compares with the
file on disk.

|`spec`
|The spec that tib generated the files from: the spec file, or the spec of the service with the
entities that the DDL yields, with every default and every derived value written out. A run of
`tib generate entity --ddl` builds on it.

|`files`
|Every file that tib wrote into the service, in the order of their paths, without the state file
itself.

|`files[].path`
|The path of the file.

|`files[].owner`
|What tib does with the file on later runs: `generator`, written on every run and not to be
edited; `developer`, written once and yours from then on; `shared`, edited in place and never
replaced, which the default pack does not write.

|`files[].sha256`
|The SHA-256 of the content of the file as tib wrote it, which `tib status` compares with the file
on disk.
|===

Every path is relative to the directory of the service and separated by `/`, on Windows too, so
that the file is the same on every machine. An input on another drive than the service keeps its
whole path.

`tib status` reads every input again from its path. One whose content changed since is listed as
`changed`, and makes it exit with 1 until tib runs with it again; one that is no longer there,
such as a spec file that was moved, is listed as `absent` and is no problem.

The next run of `tib generate entity` forgets an input that is no longer there, and a run with a
spec file forgets every other input, as the spec now comes from that file alone. The spec keeps
what was read from them, and the run names them on the standard error:

[source,text]
----
tib no longer reads the spec from these files, and forgets them:
  vehicle-service.sql
----

When the spec no longer generates a file, as when an entity leaves the spec or loses its DTO or its
API, the next run deletes the file and its record: a file of the generator's always, and a file of
the developer's when its hash is still that of the record, so that a file that you did not touch
goes with the entity. The directories that this leaves empty go too. A file of the developer's
that you edited stays, with its record, and the run names it on the standard error:

[source,text]
----
tib no longer generates these files from the spec; they stay, as they were edited:
  src/main/java/com/example/vehicleservice/depot/Depot.java
Delete them if the service no longer needs them.
----

A migration always stays, as the database may have run it; dropping the table is a new migration
of yours. A file that tib wrote when the service was created is not the entity's, and stays too.
When the entity comes back to the spec, its files that were deleted are written again. Like every
other change, the deletions show in the diff of `--dry-run`, and wait for the changes of the
service to be committed.

== Problems

A directory without a state file is not a tib project, and `tib generate entity` and
`tib status` refuse it:

[source,text]
----
/home/you/elsewhere is not a tib project: there is no .tib/state.yaml
Run tib init service first.
----

A state file that tib cannot read is refused with every problem it has, each named by the path of
its value, and tib writes nothing:

[source,text]
----
/home/you/vehicle-service: the state file has a problem: files[2].owner: required
----

A service that was generated for another stack than the one of the pack, or by a tib before 0.3.0,
which generated Spring Boot 3, is refused by `tib generate entity`: the files that tib wrote once,
such as the build and the tests, are of that stack, and what it would write now would not fit
them. `tib status` still reads it. The tib that wrote the service goes on with it, until the
service moves to the stack of the pack:

[source,text]
----
/home/you/vehicle-service was generated for an earlier stack by tib 0.2.0; pack default 0.3.0 generates for Spring Boot 4
Run tib 0.2.0 on it until the service moves to Spring Boot 4.
----

== Versions

tib reads the state files that earlier versions of tib wrote, and writes its own format with its
next run. A state file that a newer tib wrote is refused before anything else in it is read, since
it may hold what this tib does not know:

[source,text]
----
/home/you/vehicle-service: .tib/state.yaml was written by tib 0.3.0, which is newer than this tib 0.2.0; upgrade tib
----

tib 0.1.0 does not compare the versions, and cannot read a state file that tib 0.2.0 or later
wrote.
