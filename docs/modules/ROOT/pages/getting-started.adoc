= Getting started
:description: Scaffolding the first service with tib.

With tib xref:install.adoc[installed], check that it answers:

[source,bash]
----
$ tib --version
tib 0.2.0
----

== A new service

`tib init service` scaffolds a Spring Boot service: its Gradle build, the application class and
its configuration, a test and a test application that run it against PostgreSQL in a container,
a `.gitattributes` that keeps the line feeds of its text files on every platform, and
`AGENTS.md`, the notes for whoever, or whatever, works on the service next. First see what it
would write, as a diff, without writing anything:

[source,bash]
----
$ mkdir vehicle-service && cd vehicle-service
$ tib init service vehicle-service --dry-run
--- /dev/null
+++ b/.gitattributes
@@ -0,0 +1,3 @@
+# Written by tib when the service was created; it is yours from then on.
+# Text files keep their line feeds on every platform, as tib wrote them and compares them.
+* text=auto eol=lf
...
----

Then write it:

[source,bash]
----
$ tib init service vehicle-service
Wrote 11 files to /home/you/vehicle-service.
----

The eleventh file is `.tib/state.yaml`: what tib generated, with the spec it generated it from and
every file with its owner. Commit it with the service; xref:state.adoc[] says what it holds.

The service comes without the Gradle wrapper. With Gradle 9 installed, `gradle wrapper` adds it;
from then on `./gradlew build` builds the service and runs its test, which wants Docker, and
`./gradlew bootTestRun` starts the service against PostgreSQL in a container:

[source,bash]
----
$ gradle wrapper
$ ./gradlew build
$ ./gradlew bootTestRun
----

To scaffold the service from a xref:spec.adoc[spec file] instead of its name, which names its
group, its pack and its entities, give the file instead of the name:

[source,bash]
----
$ tib init service --spec vehicle-service.yaml
----

== The entities

With xref:spec.adoc#_an_example[the example spec] saved as `vehicle-service.yaml`,
`tib generate entity` adds the entity layer of every entity it names:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml --dry-run
--- a/.tib/state.yaml
+++ b/.tib/state.yaml
...
$ tib generate entity --spec vehicle-service.yaml
Wrote 23 files to /home/you/vehicle-service.
----

For `Vehicle` that is, in the package `com.example.vehicleservice.vehicle`: `VehicleGenerated`,
the mapped superclass with the columns, `VehicleDto` and `VehicleMapper`, written on every run;
`Vehicle`, the entity for your code, `VehicleRepository`, and `VehicleService` and
`VehicleController`, a CRUD API under `/api/vehicles`, written once; and the Flyway migration
`V2__create_vehicle.sql`, written once and numbered after the migrations already there.

Its tests come with it, written once, in the same package under `src/test/java`:
`VehicleRepositoryTests` saves and reads a vehicle, `VehicleApiTests` calls every operation of
the API over HTTP, both against PostgreSQL in a container, and `VehicleServiceTests` tests the
service with its repository and mapper mocked. They fill the entity with sample values that fit
its columns; `./gradlew build` runs them. An entity without a service and a controller, because
its spec turns off its DTO or its mapper, gets the repository test only.

The state file now also names the spec file that the entities came from, relative to the service,
with the hash of its content when tib read it:

[source,yaml]
----
# Written by tib on every run. Do not edit: your changes would be lost.
tib: 0.2.0
pack:
  name: default
  version: 0.2.0
inputs:
- kind: spec
  path: vehicle-service.yaml
  sha256: 574dbfdaa1431ba5e7301ba45d919128b46f13e705ed5e6dab2b1f5421afcbfe
spec:
  ...
----

Run it again after a change of the spec: the files written on every run follow the spec, and the
files written once stay yours, also when you delete one. A run that would change nothing says so,
and changes nothing:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml
Nothing to change.
----

In a git repository, tib writes only when the files of the service that git tracks have no
uncommitted changes, so that what tib changed can be told apart from what you changed. Commit or
stash yours first, the change of a spec file that git tracks included; `--allow-dirty` writes
anyway, and `--dry-run` writes nothing, so it always runs. Files that git does not track, such as
a new spec file, do not count. After a change of the committed spec, with an edit of `Vehicle.java`
not committed either:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml
/home/you/vehicle-service has changes that are not committed:
   M src/main/java/com/example/vehicleservice/vehicle/Vehicle.java
   M vehicle-service.yaml
Commit or stash them first, so that the changes of tib can be told apart, or run again with --allow-dirty.
----

The entities may come from the tables of SQL DDL instead, which tib adds to the spec of the
service; xref:ddl.adoc[] says what it reads:

[source,bash]
----
$ tib generate entity --ddl vehicle-service.sql
----

== What tib owns

Each generated file says in its first line what tib does with it on later runs. A file *written
once* is yours from then on; one *written on every run*, such as `VehicleGenerated.java`, is
replaced by tib, so it is not to be edited.

`tib status` says which of them are no longer as tib wrote them. A file of tib's that was edited
or is missing is a problem, and makes it exit with 1, so that a build can check for it:
`git checkout` restores it, or the next run of tib writes it again, with `--allow-dirty` while the
change is not committed. A file of yours that was removed stays removed:

[source,bash]
----
$ tib status
vehicle-service: tib 0.2.0, pack default 0.2.0, 2 entities, 32 files.
edited   src/main/java/com/example/vehicleservice/vehicle/VehicleMapper.java
removed  src/main/java/com/example/vehicleservice/vehicle/VehicleService.java

An edited file is written by tib on every run: git checkout restores it, or the next run of tib replaces it, with --allow-dirty while the edit is not committed.
A removed file was yours: tib does not write it again.
----

`tib --help` lists the commands, and `tib <command> --help` the options of one. Every command and
option is also in the xref:reference/tib.adoc[reference].
