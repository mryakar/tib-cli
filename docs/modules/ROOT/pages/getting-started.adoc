= Getting started
:description: Scaffolding the first service with tib.

With tib xref:install.adoc[installed], check that it answers:

[source,bash]
----
$ tib --version
tib 0.4.0
----

== A new service

`tib init service` scaffolds a service: its Gradle build and Gradle wrapper, the application class
and its configuration, a test and a test application that run it against PostgreSQL in a
container, a `.gitattributes` that keeps the line ends of its files on every platform, and
`AGENTS.md`, the notes for the next developer or agent. Without options it is a Spring Boot 4
service in the anemic architecture, on Java 21. First see what it would write, as a diff, without
writing anything:

[source,bash]
----
$ mkdir vehicle-service && cd vehicle-service
$ tib init service vehicle-service --dry-run
--- /dev/null
+++ b/.gitattributes
@@ -0,0 +1,6 @@
+# Written by tib when the service was created; it is yours from then on.
+# Text files keep their line feeds on every platform, as tib wrote them and compares them.
+* text=auto eol=lf
+# Batch files, such as gradlew.bat, keep the carriage returns that cmd.exe expects.
+*.bat text eol=crlf
+*.cmd text eol=crlf
...
----

A file that is not text, such as the jar of the Gradle wrapper, shows as a line that says it
differs, as in git. Then write it:

[source,bash]
----
$ tib init service vehicle-service
Wrote 15 files to /home/you/vehicle-service.
----

The fifteenth file is `.tib/state.yaml`: what tib generated, with the spec it generated it from and
every file with its owner. Commit it with the service; xref:state.adoc[] says what it holds.

The service comes with the Gradle wrapper of the Gradle that tib is built with, so it needs no
Gradle of its own; the wrapper is yours, and `./gradlew wrapper --gradle-version <version>` moves
it to another Gradle. `./gradlew build` builds the service and runs its test, which wants Docker,
and `./gradlew bootTestRun` starts the service against PostgreSQL in a container:

[source,bash]
----
$ ./gradlew build
$ ./gradlew bootTestRun
----

== The choices

Five options choose what the service is made with. Each has a property of the same name in the
xref:spec.adoc[spec file]:

[cols="2,4,2"]
|===
|Option |Values |Default

|`--pack`
|`default`, a Spring Boot 4 service; `plain`, a service in plain Java. xref:packs.adoc[] compares
the two.
|`default`

|`--java`
|`21` or `25`. The build of the service compiles with a JDK of its Java, which Gradle looks for on
the machine.
|`21`

|`--architecture`
|`anemic`, `ddd` or `hexagonal`. xref:architectures.adoc[] says where each puts the classes.
|`anemic`

|`--tests`
|`unit`, `integration`, `api` and `archunit`, separated by commas, or `none`.
|`unit,integration,api`

|`--docker`
|A `Dockerfile` and a `.dockerignore`, both yours.
|no `Dockerfile`
|===

[source,bash]
----
$ tib init service vehicle-service --java 25 --architecture ddd --tests unit,api,archunit --docker
$ tib init service fleet-service --pack plain --architecture hexagonal
----

The kinds of tests:

* `unit` writes the tests of the service of every entity, with what the service uses mocked.
* `integration` writes the tests of the repository of every entity against PostgreSQL in a
  container, and the test of the application.
* `api` writes the tests of the API of every entity against the running service.
* `archunit` writes `ArchitectureTests`: the rules of the architecture, which ArchUnit checks on
  the classes of the service.

A service without `integration` and `api` builds without Docker.

The `Dockerfile` builds the service with its Gradle wrapper and runs it on the Java runtime of its
version, as a user without root rights. In a container, the service reaches its database through
the environment: `SPRING_DATASOURCE_URL` with the default pack, `DATABASE_URL` with the plain one.

[source,bash]
----
$ docker build -t vehicle-service .
----

`--pack` also takes the pack with its version after an at sign, as the spec does. A value that tib
cannot use, such as a Java version that is not 21 or 25, a kind of test that tib does not know or
a name that is not the name of a service, is an error of the command line: tib says what is wrong,
writes nothing and exits with 2.

Each choice is made when the service is created.
xref:spec.adoc#_the_rules[A later spec that gives another is refused].

=== The questions

Without a name and without a spec file, tib asks for the name and for what the options choose:
the template pack, the Java version, the architecture, the kinds of tests and the Dockerfile. An
empty answer takes the default in brackets, and an answer that tib cannot use is asked again. The
questions go to standard error and the answers come from standard input, so that a dry run still
prints only its diff. When standard input ends before the last answer, as in a script, tib writes
nothing and exits with 2.

[source,text]
----
$ tib init service
The name of the service, in lower case words joined with hyphens: vehicle-service
Its template pack: default, plain [default]:
Its Java version, 21 or 25 [21]: 25
Its architecture: anemic, ddd, hexagonal [anemic]:
The kinds of its tests, separated by commas, or none: unit, integration, api, archunit [unit,integration,api]: unit,api
A Dockerfile, yes or no [no]: yes
Wrote 16 files to /home/you/vehicle-service.
----

=== A spec file

A xref:spec.adoc[spec file] names the service with its group, pack, Java, architecture, kinds of
tests, Dockerfile and entities. Give it in place of the name:

[source,bash]
----
$ tib init service --spec vehicle-service.yaml
----

== The entities

With xref:spec.adoc#_an_example[the example spec] saved as `vehicle-service.yaml`,
`tib generate entity` adds the entity layer of every entity it names:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml --dry-run
--- a/.tib/state.yaml
+++ b/.tib/state.yaml
...
$ tib generate entity --spec vehicle-service.yaml
Wrote 26 files to /home/you/vehicle-service.
----

For `Vehicle` that is, in the package `com.example.vehicleservice.vehicle`: `VehicleGenerated`,
the mapped superclass with the columns, `VehicleDto` and `VehicleMapper`, written on every run;
`Vehicle`, the entity for your code, `VehicleRepository`, and `VehicleService` and
`VehicleController`, a CRUD API under `/api/vehicles`, written once; and the Flyway migration
`V2__create_vehicle.sql`, written once and numbered after the migrations already there. The API
lists the vehicles in the order of their identifiers, in pages unless the spec turns `pagination`
off. The Java that tib writes is in the layout of google-java-format, so that a run of it leaves
the files as they are.

These are the classes of the default pack in the anemic architecture. xref:architectures.adoc[]
lists the classes and their packages in each architecture, and xref:packs.adoc[] says what the
plain pack writes instead.

The first entity with an API also brings `ConflictHandler`, in `com.example.vehicleservice`,
written once: a request that breaks a constraint of the database, such as a plate number that
another vehicle has or a depot that vehicles refer to, gets `409 Conflict`, as a problem detail
that does not name the constraint:

[source,json]
----
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "The request breaks a constraint of the database.",
  "instance": "/api/depots/fa8b065a-0851-4b16-9985-bcb5a9cd1c9f"
}
----

The tests of `Vehicle` come with it, written once, in the same package under `src/test/java`:
`VehicleRepositoryTests` saves and reads a vehicle, `VehicleApiTests` calls every operation of
the API over HTTP, both against PostgreSQL in a container, and `VehicleServiceTests` tests the
service with its repository and mapper mocked. For an entity with a unique value,
`VehicleApiTests` also checks that a second one with the same value gets `409 Conflict`. They take
their vehicles from `VehicleSamples`, written on every run, which builds a vehicle or its DTO with
sample values that fit its columns; a test changes a value through the builder, as in
`VehicleSamples.vehicle().capacity(40).build()`, and the samples follow the spec when it changes.
`./gradlew build` runs them. An entity without a service and a controller, because its spec turns
off its DTO or its mapper, gets the repository test only. A service has only the tests of the
kinds it chose.

The state file now also names the spec file that the entities came from, relative to the service,
with the hash of its content when tib read it:

[source,yaml]
----
# Written by tib on every run. Do not edit: your changes would be lost.
tib: 0.4.0
pack:
  name: default
  version: 0.4.0
  stack: Spring Boot 4
inputs:
- kind: spec
  path: vehicle-service.yaml
  sha256: 574dbfdaa1431ba5e7301ba45d919128b46f13e705ed5e6dab2b1f5421afcbfe
spec:
  ...
----

Run it again after a change of the spec: the files written on every run follow the spec, and the
files written once stay yours, also when you delete one. An entity that leaves the spec takes its
files with it, but for those you edited and its migration; xref:state.adoc[] says which. A run
that would change nothing says so, and changes nothing:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml
Nothing to change.
----

In a git repository, tib writes only when the files of the service that git tracks have no
uncommitted changes, so that what tib changed can be told apart from what you changed. Commit or
stash yours first, the change of a spec file that git tracks included; `--allow-dirty` writes
anyway, and `--dry-run` writes nothing, so it always runs. Files that git does not track, such as
a new spec file, do not count. After a change of the committed spec, with an edit of `Vehicle.java`
not committed either:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml
/home/you/vehicle-service has changes that are not committed:
   M src/main/java/com/example/vehicleservice/vehicle/Vehicle.java
   M vehicle-service.yaml
Commit or stash them first, so that the changes of tib can be told apart, or run again with --allow-dirty.
----

In a service scaffolded from its name, the entities may come from the tables of SQL DDL instead,
which tib adds to the spec of the service; xref:ddl.adoc[] says what it reads:

[source,bash]
----
$ tib generate entity --ddl vehicle-service.sql
----

== What tib owns

Each generated file, but for those of the Gradle wrapper, says in its first line what tib does
with it on later runs. A file *written once* is yours from then on; one *written on every run*,
such as `VehicleGenerated.java`, is replaced by tib, so it is not to be edited.

`tib status` says which of them are no longer as tib wrote them, and which of the files that it
read the spec from were changed since, and exits with 1 when a file has to be restored or tib has
to run again, so that a build can check for it:

[source,bash]
----
$ tib status
vehicle-service: tib 0.4.0, pack default 0.4.0, 2 entities, 39 files.

Read from:
changed  vehicle-service.yaml

Files:
edited   src/main/java/com/example/vehicleservice/vehicle/VehicleMapper.java
removed  src/main/java/com/example/vehicleservice/vehicle/VehicleService.java

A changed input was edited after tib read the spec from it: the files of tib's follow it once tib runs with it again.
An edited file is written by tib on every run: git checkout restores it, or the next run of tib replaces it, with --allow-dirty while the edit is not committed.
A removed file was yours: tib does not write it again.
----

`tib --help` lists the commands, and `tib <command> --help` the options of one. Every command and
option is also in the xref:reference/tib.adoc[reference].
