= Getting started
:description: Scaffolding the first service with tib.

With tib xref:install.adoc[installed], check that it answers:

[source,bash]
----
$ tib --version
tib 0.4.0
----

== A new service

`tib init service` scaffolds a Spring Boot 4 service: its Gradle build and Gradle wrapper, the
application class and its configuration, a test and a test application that run it against
PostgreSQL in a container, a `.gitattributes` that keeps the line feeds of its text files on every
platform and the carriage returns of its batch files, and `AGENTS.md`, the notes for whoever, or
whatever, works on the service next; with `--pack plain`, a service in plain Java instead, as
<<_a_service_in_plain_java>> says. First see what it would write, as a diff, without writing
anything:

[source,bash]
----
$ mkdir vehicle-service && cd vehicle-service
$ tib init service vehicle-service --dry-run
--- /dev/null
+++ b/.gitattributes
@@ -0,0 +1,6 @@
+# Written by tib when the service was created; it is yours from then on.
+# Text files keep their line feeds on every platform, as tib wrote them and compares them.
+* text=auto eol=lf
+# Batch files, such as gradlew.bat, keep the carriage returns that cmd.exe expects.
+*.bat text eol=crlf
+*.cmd text eol=crlf
...
----

A file that is not text, such as the jar of the Gradle wrapper, shows as a line that says it
differs, as in git. Then write it:

[source,bash]
----
$ tib init service vehicle-service
Wrote 15 files to /home/you/vehicle-service.
----

The fifteenth file is `.tib/state.yaml`: what tib generated, with the spec it generated it from and
every file with its owner. Commit it with the service; xref:state.adoc[] says what it holds.

The service comes with the Gradle wrapper of the Gradle that tib is built with, so it needs no
Gradle of its own; the wrapper is yours, and `./gradlew wrapper --gradle-version <version>` moves
it to another Gradle. `./gradlew build` builds the service and runs its test, which wants Docker,
and `./gradlew bootTestRun` starts the service against PostgreSQL in a container:

[source,bash]
----
$ ./gradlew build
$ ./gradlew bootTestRun
----

The service is on Java 21. `--java 25` puts it on Java 25 instead; either way, its build compiles
with a JDK of its Java, which Gradle looks for on the machine:

[source,bash]
----
$ tib init service vehicle-service --java 25
----

Every entity gets tests of three kinds: `unit`, the tests of its service with the repository and
the mapper mocked; `integration`, the tests of its repository against PostgreSQL in a container,
which come with the test of the application; and `api`, the tests of its API against the running
service. A fourth kind, `archunit`, is the test of the architecture of the service: rules that
ArchUnit checks on its classes. `--tests` keeps the kinds you name, separated by commas; with
`--tests unit`, the build of the service needs no Docker:

[source,bash]
----
$ tib init service vehicle-service --tests unit,api
----

The code of the service is arranged in the anemic architecture: the classes of an entity in its
package, the controller over the service over the repository. `--architecture ddd` arranges it for
domain-driven design instead: every entity is an aggregate in three packages, its `domain` with
the entity and its repository, its `application` with the service of its use cases, and its `web`
with its controller, DTO and mapper; an entity refers to another by its identifier, as `depotId`,
not by the entity. `--architecture hexagonal` arranges it in ports and adapters: the domain of
every entity is in plain Java, without JPA or Spring, in its `domain`; its `application` has the
service of its use cases and the ports, `application.port.in` with the use cases that the
controller calls and `application.port.out` with the store that keeps the domain; its
`adapter.in.web` has the controller, DTO and mapper, and its `adapter.out.persistence` the JPA
entity of its table, its repository, the mapper between the two and the adapter of the store. An
entity refers to another by its identifier there too. `archunit` checks the rules of the
architecture the service has.

[source,bash]
----
$ tib init service vehicle-service --architecture ddd --tests unit,integration,api,archunit
$ tib init service fleet-service --architecture hexagonal --tests unit,integration,api,archunit
----

`--docker` adds a `Dockerfile` and a `.dockerignore`, both yours. The `Dockerfile` builds the
service with its Gradle wrapper and runs it on the Java runtime of its version, as a user without
root rights; in a container, the service reaches its database through the environment, as
`SPRING_DATASOURCE_URL`:

[source,bash]
----
$ tib init service vehicle-service --docker
$ docker build -t vehicle-service .
----

Without the name and without a spec file, tib asks for what the command line would say: the name,
the Java version, the template pack, the architecture, the kinds of tests and the Dockerfile. An empty answer takes the default in
brackets, and an answer that tib cannot use is asked again. The questions go to standard error and
the answers come from standard input, so that a dry run still prints only its diff; when standard
input ends before the last answer, as in a script, tib writes nothing and exits with 2.

[source,text]
----
$ tib init service
The name of the service, in lower case words joined with hyphens: vehicle-service
Its Java version, 21 or 25 [21]: 25
Its template pack: default, plain [default]:
Its architecture: anemic, ddd, hexagonal [anemic]:
The kinds of its tests, separated by commas, or none: unit, integration, api, archunit [unit,integration,api]: unit,api
A Dockerfile, yes or no [no]: yes
Wrote 16 files to /home/you/vehicle-service.
----

To scaffold the service from a xref:spec.adoc[spec file] instead of its name, which names its
group, its pack, its Java, its architecture, its kinds of tests, whether it has a Dockerfile, and
its entities, give the file instead of the name:

[source,bash]
----
$ tib init service --spec vehicle-service.yaml
----

== The entities

With xref:spec.adoc#_an_example[the example spec] saved as `vehicle-service.yaml`,
`tib generate entity` adds the entity layer of every entity it names:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml --dry-run
--- a/.tib/state.yaml
+++ b/.tib/state.yaml
...
$ tib generate entity --spec vehicle-service.yaml
Wrote 26 files to /home/you/vehicle-service.
----

For `Vehicle` that is, in the package `com.example.vehicleservice.vehicle`: `VehicleGenerated`,
the mapped superclass with the columns, `VehicleDto` and `VehicleMapper`, written on every run;
`Vehicle`, the entity for your code, `VehicleRepository`, and `VehicleService` and
`VehicleController`, a CRUD API under `/api/vehicles`, written once; and the Flyway migration
`V2__create_vehicle.sql`, written once and numbered after the migrations already there. The Java
that tib writes is in the layout of google-java-format, so that a run of it leaves the files as
they are.

The first entity with an API also brings `ConflictHandler`, in `com.example.vehicleservice`,
written once: a request that breaks a constraint of the database, such as a plate number that
another vehicle has or a depot that vehicles refer to, gets `409 Conflict`, as a problem detail
that does not name the constraint:

[source,json]
----
{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "detail": "The request breaks a constraint of the database.",
  "instance": "/api/depots/fa8b065a-0851-4b16-9985-bcb5a9cd1c9f"
}
----

Its tests come with it, written once, in the same package under `src/test/java`:
`VehicleRepositoryTests` saves and reads a vehicle, `VehicleApiTests` calls every operation of
the API over HTTP, both against PostgreSQL in a container, and `VehicleServiceTests` tests the
service with its repository and mapper mocked. For an entity with a unique value,
`VehicleApiTests` also checks that a second one with the same value gets `409 Conflict`. They take
their vehicles from `VehicleSamples`, written on every run, which builds a vehicle or its DTO with
sample values that fit its columns; a test changes a value through the builder, as in
`VehicleSamples.vehicle().capacity(40).build()`, and the samples follow the spec when it changes.
`./gradlew build` runs them. An entity without a service and a controller, because its spec turns
off its DTO or its mapper, gets the repository test only.

The state file now also names the spec file that the entities came from, relative to the service,
with the hash of its content when tib read it:

[source,yaml]
----
# Written by tib on every run. Do not edit: your changes would be lost.
tib: 0.4.0
pack:
  name: default
  version: 0.4.0
  stack: Spring Boot 4
inputs:
- kind: spec
  path: vehicle-service.yaml
  sha256: 574dbfdaa1431ba5e7301ba45d919128b46f13e705ed5e6dab2b1f5421afcbfe
spec:
  ...
----

Run it again after a change of the spec: the files written on every run follow the spec, and the
files written once stay yours, also when you delete one. An entity that leaves the spec takes its
files with it, but for those you edited and its migration; xref:state.adoc[] says which. A run
that would change nothing says so, and changes nothing:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml
Nothing to change.
----

In a git repository, tib writes only when the files of the service that git tracks have no
uncommitted changes, so that what tib changed can be told apart from what you changed. Commit or
stash yours first, the change of a spec file that git tracks included; `--allow-dirty` writes
anyway, and `--dry-run` writes nothing, so it always runs. Files that git does not track, such as
a new spec file, do not count. After a change of the committed spec, with an edit of `Vehicle.java`
not committed either:

[source,bash]
----
$ tib generate entity --spec vehicle-service.yaml
/home/you/vehicle-service has changes that are not committed:
   M src/main/java/com/example/vehicleservice/vehicle/Vehicle.java
   M vehicle-service.yaml
Commit or stash them first, so that the changes of tib can be told apart, or run again with --allow-dirty.
----

In a service scaffolded from its name, the entities may come from the tables of SQL DDL instead,
which tib adds to the spec of the service; xref:ddl.adoc[] says what it reads:

[source,bash]
----
$ tib generate entity --ddl vehicle-service.sql
----

== A service in plain Java

`--pack plain` scaffolds the service with the `plain` pack instead of the default one: a service in
plain Java, without a framework of dependency injection, whose objects are wired by hand in its
application class. It answers HTTP with the server of the JDK, `com.sun.net.httpserver`, keeps its
entities in PostgreSQL with JDBC, without a pool, migrates its schema with Flyway when it starts,
and reads and writes JSON with Jackson; its tests use JUnit, Mockito and Testcontainers. The pack
arranges a service in all three architectures. The same is `pack: plain` in the spec.

[source,bash]
----
$ tib init service vehicle-service --pack plain
$ ./gradlew build
$ ./gradlew testRun
----

Its build is Gradle's `application`: `./gradlew run` starts the service against the database that
the environment names, through `Config`, `./gradlew testRun` against PostgreSQL in a container, and
`./gradlew installDist` installs it under `build/install`, which its `Dockerfile` runs:

[cols="1,2,2"]
|===
|Variable |What |Default

|`DATABASE_URL`
|The JDBC URL of the database.
|`jdbc:postgresql://localhost:5432/vehicle_service`, the name of the service with underscores

|`DATABASE_USER`
|The user of the database.
|`vehicle_service`

|`DATABASE_PASSWORD`
|The password of the user.
|`vehicle_service`

|`PORT`
|The port of the API.
|`8080`
|===

`tib generate entity` adds, for every entity, in its package: `VehicleGenerated`, the plain Java
values of its columns, a relation as the identifier of its target, as `depotId`;
`VehicleRepository`, the SQL of its table on JDBC; `VehicleDto`, which checks what the spec
requires and the length of a `String` itself; and `VehicleMapper`, all written on every run; and
`Vehicle`, `VehicleService`, the use cases on the DTOs, each in a transaction, and `VehicleHandler`,
the API under `/api/vehicles` as the default pack's, pages included, written once. The migrations
are the default pack's. `Routes`, in the base package, is written on every run: it wires the
classes of every entity by hand and puts its handler at its path, so that a new entity needs no
change of the application class. `ErrorHandler`, written with the first entity, answers an entity
that is not there with `404 Not Found`, a broken constraint of the database with `409 Conflict` and a
DTO that breaks a rule or does not read with `400 Bad Request`, as problem details. The tests are
of the same kinds: `XRepositoryTests` and the test of the application against PostgreSQL in a
container, `XServiceTests` with the repository and the mapper mocked, `XApiTests` over HTTP with the
JDK's client, and `ArchitectureTests`, whose rules go by the names and the packages of the classes.

With `--architecture ddd`, the same classes are arranged in three packages of the entity, as with
the default pack: `vehicle.domain` has `Vehicle`, `VehicleGenerated` and `VehicleRepository`;
`vehicle.application` has `VehicleService`, whose use cases take and give the aggregate and throw
`NotFoundException` for one that is not there; and `vehicle.web` has `VehicleHandler`, which maps
the aggregate to and from `VehicleDto` with `VehicleMapper`. `XServiceTests` mock the repository
only, and `ArchitectureTests` has the rules of DDD, which go by the packages of the classes.

With `--architecture hexagonal`, the domain of every entity is in plain Java that knows neither
JDBC nor the HTTP server: `vehicle.domain` has `Vehicle` and `VehicleGenerated`;
`vehicle.application` has `VehicleService`, which implements `VehicleUseCase`, the port that the
inbound adapters call, in `vehicle.application.port.in`, and keeps the domain through
`VehicleStore`, the port in `vehicle.application.port.out`. `vehicle.adapter.in.web` has
`VehicleHandler`, `VehicleDto` and `VehicleWebMapper`; `vehicle.adapter.out.persistence` has
`VehicleRepository`, the SQL of the table, and `VehiclePersistenceAdapter`, the store on it, which
joins the transaction of the use case and turns a failure of JDBC into one of `Transactions`.
`XPersistenceAdapterTests` test the store against PostgreSQL, in place of `XRepositoryTests`;
`XServiceTests` mock the store; and `ArchitectureTests` has the rules of the hexagonal
architecture, which go by the packages of the classes.

A service stays with its pack: `tib generate entity` refuses a spec of the other one, which
generates for another stack.

== What tib owns

Each generated file, but for those of the Gradle wrapper, says in its first line what tib does
with it on later runs. A file *written once* is yours from then on; one *written on every run*,
such as `VehicleGenerated.java`, is replaced by tib, so it is not to be edited.

`tib status` says which of them are no longer as tib wrote them, and which of the files that it
read the spec from were changed since, and exits with 1 when a file has to be restored or tib has
to run again, so that a build can check for it:

[source,bash]
----
$ tib status
vehicle-service: tib 0.4.0, pack default 0.4.0, 2 entities, 39 files.

Read from:
changed  vehicle-service.yaml

Files:
edited   src/main/java/com/example/vehicleservice/vehicle/VehicleMapper.java
removed  src/main/java/com/example/vehicleservice/vehicle/VehicleService.java

A changed input was edited after tib read the spec from it: the files of tib's follow it once tib runs with it again.
An edited file is written by tib on every run: git checkout restores it, or the next run of tib replaces it, with --allow-dirty while the edit is not committed.
A removed file was yours: tib does not write it again.
----

`tib --help` lists the commands, and `tib <command> --help` the options of one. Every command and
option is also in the xref:reference/tib.adoc[reference].
