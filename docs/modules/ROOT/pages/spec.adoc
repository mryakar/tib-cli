= The spec file
:description: The YAML file that tells tib what to generate, and its JSON Schema.

A spec is a YAML file that says what tib generates: the service, its group and template pack,
and its entities with their fields and relations. `tib init service --spec` scaffolds the service
from it, and `tib generate entity --spec` adds the entity layer of its entities.

== What tib derives

Some values follow from others, always the same way:

* The base package is the group with the service's name without its hyphens,
  `com.example.vehicleservice`, and the package of an entity is the base package with the
  entity's name in lower case, `com.example.vehicleservice.vehicle`.
* An identifier without a strategy gets `identity` when it is a `Long` and `uuid` when it is a
  `UUID`.
* A `String` without a length gets 255 from the default pack: in its column, in the validation of
  its DTO and in its migration.
* Without the DTO, or without the mapper, an entity has no service and no controller either. A
  DTO without a mapper is there for a mapper that you write.
* `pagination` acts when the entity is created: the service and the controller are written once,
  so a later change of the option leaves them as they are.

== The schema

`tib schema` prints the JSON Schema of the spec, which an editor uses for completion and
validation:

[source,bash]
----
tib schema > tib-spec.schema.json
----

With the https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml[YAML extension]
of VS Code, the first line of the spec names the schema:

[source,yaml]
----
# yaml-language-server: $schema=tib-spec.schema.json
----

In IntelliJ IDEA, map the file to the schema under _Settings › Languages & Frameworks › Schemas and
DTDs › JSON Schema Mappings_.

The schema of this version of tib is also here: xref:attachment$tib-spec.schema.json[tib-spec.schema.json].

== The rules

`tib` checks the rules of the schema, and the rules below that tie one value to another, which a
schema does not hold. A problem names the value it is about, as in
`entities[0].fields[2].length`, and tib writes nothing.

* `tib` is `1`, the version of the spec format that this tib reads; a later one is refused, as in
  `tib: 2 is above 1`.
* Every entity has a name of its own and a table of its own, and every member of an entity, its
  identifier, fields and relations, a name of its own and a column of its own. Tables and columns
  are compared in any case; the columns of an audited entity include `CREATED_AT` and
  `UPDATED_AT`.
* No name becomes a Java keyword: not a field, an identifier or the field of a relation (`class`),
  not a part of the group (`com.new`), not the service's name without its hyphens, and not the
  name of an entity in lower case, which is its package (`Class`).
* No table or column is a word that PostgreSQL reserves, in any case: an entity `User` needs a
  table other than `USER`, and a field `order` a column other than `ORDER`, as the problem says:
  `'USER' is a reserved word in SQL; give the entity a table`.
* Only a `String` has a `length`; only a `BigDecimal` has a `precision` and a `scale`, and its
  scale is not above its precision.
* An identifier's strategy is `identity` or `sequence` for a `Long` and `uuid` for a `UUID`.
* A relation's target is an entity of the spec, and the relations make no cycle: an entity that
  refers to another may not be referred to by it, directly or through others. A relation of an
  entity to itself is allowed.
